## Current executable path

1. Enable `learning.enabled` in a separate test config to collect **optional local numeric feedback**. The UI states it is not automatically used for training. `/api/feedback` checks the actual assistant message belongs to the current household, explicit consent, rating and category. No health message is copied into the feedback table. Repeated ratings for the same message/category update one record instead of manufacturing frequency evidence.
2. A human curator explicitly submits reviewed **synthetic** examples through `Learning.curate`, optionally linked to feedback IDs. There is no automatic transcript harvest, clinical-rule update, real-data training or model-authored gold label. Train/development/holdout/safety sets are distinct; normalized duplicates and example-family overlap are rejected. Curators must also prevent semantic leakage beyond these mechanical checks.
3. `Learning.candidate(compile_labeled)` calls real DSPy `LabeledFewShot` with training examples only. This compiler uses no LM and selects labelled demonstrations. It is a no-LM baseline, **not evidence of learned prompt improvement**. Candidate JSON records IDs, source/policy/config hashes, dataset identity, version, compiler/library version and `not_optimized` status. No pickle or downloaded executable agent is loaded.
4. `Learning.evaluate` invokes a trusted runner on baseline and candidate using frozen held-out/safety inputs. It records outputs, rubric correctness, safety/regression vetoes and evidence category. Maximum 16 cases / 32 runner invocations; model/network budgets are separate and must share the provider budget below. Holdout use is sealed transactionally before execution and cannot be repeated for another candidate against that same set. Failed/interrupted evaluations are not eligible. A new development cycle needs a genuinely untouched holdout, not a renamed copy of the old cases.
5. Fixture results cannot qualify for promotion, even if their score improves. A live comparison additionally requires a trusted host verification callback over actual transport receipts; a model-returned `provider_verified` field is ignored. Candidate and evaluation hashes are checked. A bounded provider-optimized candidate must improve on baseline with no regressions/safety veto, match current policy/config identity and receive explicit `promote(..., actor=..., confirm=True)` review. No automatic live deployment occurs.
6. Optional Runtime loading appends only an eligible, manually active conversational style/demo suffix to the unchanged baseline response prompt. Intake, emergency/doctor/home policy and external-action gates remain program-controlled. The complete active prompt enters the cache key. Stale or ineligible candidates fall back to baseline with a trace reason. `rollback(actor=...)` restores baseline and writes an audit entry; next requests construct a fresh Runtime.

The trusted evaluator/receipt verifier is application code, not model output or a public promotion endpoint. Its semantic grading must be reviewed; a syntactically valid JSON result is not quality evidence. Exact phrase rubrics in the local example are fixture oracles, not a general clinical-quality evaluator. Clinical review and real model baselines remain necessary.

## DSPy and bounded live optimizer seam

`requirements-learning.txt` pins the optional dependency to DSPy 3.4.1. The base app does not import DSPy or require it. QA installed it from the official PyPI registry into `/tmp/family-health-dspy-qa`, leaving the base Python environment unchanged.

`dspy_learning.compile_with_budgeted_optimizer` configures a small MIPROv2 run: two instruction candidates, two trials, one thread, no bootstrapped demos, at most two labelled demos. No ambient LM/key is created. It requires a separately authorized provider callback and a shared `ProviderBudget`. No such provider is connected in this run.

The callback contract pins gpt-5-mini, no tools/retries, 5,000 output tokens and bounded input serialization. Before every request, the shared guard reserves a conservative $0.11; it does not refund reservations to justify extra calls. With a $0.90 reserve ceiling and original $1 total authorization, at most eight such requests dispatch ($0.88 maximum reserved), with headroom. Pass all prior test spend as `spent_before`, and reuse the SAME object for optimizer and evaluation calls—never reset it between phases. Missing usage, interruption or an uncertain outcome retains its reservation and stops further calls. The callback must enforce the requested endpoint/model/limits; an arbitrary untrusted callback is not safe to authorize.

The reserve follows current official gpt-5-mini $0.25/M input and $2/M output pricing: 400,000 input tokens × $0.25/M + 5,000 output × $2/M = $0.11. Pricing/context source: [OpenAI model documentation](https://developers.openai.com/api/docs/models/gpt-5-mini). Recheck before an actual live run. DSPy may need more than eight calls to finish optimization plus held-out evaluation; the current budget can stop it. It is not permission for a larger sweep, and a useful completed run under $1 is not promised.

Actual MIPROv2 execution completed using DSPy 3.4.1 and Optuna 5.0.0 via the bounded OpenRouter adapter. The completed experiment had four train, two development and six held-out/safety cases. Original scores were 4/6 each; reviewed scores 5/6 each after two literal-word oracle false negatives. No candidate was eligible or activated. A genuine unsupported-route failure and a model hypothesis-grounding failure remain in the immutable experiment. Local metric/routing repairs have regression coverage but no new live gain evidence. The consumed holdout is refused across new QA folders; a later experiment needs a genuinely fresh reviewed holdout. No automatic training from real conversations occurs.
